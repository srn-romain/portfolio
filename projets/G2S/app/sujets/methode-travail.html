Méthodes de travail employées et environnement de travail


1. Méthodes de travail
Approche agile : méthodologie Scrum

Dans le cadre du projet GDE, l’équipe adopte une approche agile, spécifiquement la méthodologie Scrum. Cette méthode permet d’organiser le travail en sprints de trois semaines, assurant ainsi un développement itératif et adaptatif.

Instances principales du projet

Les principales réunions auxquelles l’équipe prend part sont les suivantes :

  • Daily : Réunion quotidienne à 9h30 pour suivre l’avancement et ajuster les priorités.
  • Sprint Planning : Réunion chaque mardi en début de sprint pour planifier les tâches et objectifs.
  • Sprint Review : Réunion chaque premier lundi du sprint pour faire le point sur les livrables du sprint précédent.
  • Rétrospective : Réunion chaque premier lundi du sprint pour identifier les axes d'amélioration du sprint précédent.
  • Démo de Sprint : Réunion un sprint sur deux, le vendredi, pour présenter les évolutions au client.
  • Extrême Cotation : Réunion occasionnelle pour anticiper et évaluer la complexité des évolutions.
  • DF Mensuel : Réunion mensuelle pour faire un point général sur l’ensemble des projets au sein de la Digital Factory (DF).

Une documentation complète sur ces réunions et le calendrier des prochaines versions est disponible sur l'outil Confluence.

Processus de développement

Le processus de développement suit plusieurs étapes définies comme suit :

  1. Capacité et Estimation de Sprint : Avant chaque Sprint Planning, le Scrum Master évalue la capacité de l'équipe, en tenant compte des facteurs externes. L'estimation repose sur la vélocité, qui mesure la capacité de l’équipe à accomplir des tâches.
  2. Assignation : Lorsqu’une User Story est prête, elle est assignée à un développeur qui commence à travailler dessus.
  3. Développement : Le développeur implémente la fonctionnalité ou corrige le bug dans le code.
  4. Test Unitaire : Le développeur écrit et exécute des tests unitaires pour vérifier que la fonctionnalité implémentée fonctionne correctement.
  5. Revue de code : Un autre développeur relit le code pour s'assurer qu'il respecte les standards de qualité et est fonctionnel.
  6. Intégration : Une fois validée, la modification est intégrée au code source principal et déployée lors des versions prévues.

La complexité des User Stories est estimée en points, selon la suite de Fibonacci, et les User Stories dépassant 10 points sont divisées en sous-tâches plus petites.

Répartition des tâches

Les User Stories sont rédigées par les Business Analystes et la Co-PO, et assignées via l'outil Jira aux développeurs pour leur implémentation.

Environnements de développement et de maturité du code

Le projet utilise plusieurs environnements de développement adaptés au cycle de vie du code :

  • Local : Le code est développé localement par les développeurs.
  • Développement (D) : Consolidation des codes des différents développeurs.
  • Recette (REC-0, REC-1) : Tests et validations fonctionnelles sur ces environnements de recette, avec un principe de rotation entre les deux environnements.
  • Préproduction (PP ou Q) : Tests dans des conditions proches de la production avant le déploiement.
  • Production (Prod) : Le code validé est déployé et mis à disposition des utilisateurs.
  • Environnements spécifiques :
    • Formation (F) : Environnement utilisé pour des sessions de formation.
    • Utilitaire (K) : Environnement pour des besoins ponctuels.
    • Performance (X) : Environnement pour les tests de performance afin d’évaluer la rapidité et identifier les points de blocage.
2. Environnement technique

Pour assurer la gestion du projet et le développement technique, plusieurs outils sont utilisés :

  • Gestion de projet : Jira pour le suivi des User Stories et Confluence pour la documentation du projet.
  • Développement : IntelliJ (IDE Java et Vue.js), GitLab (gestion de versions), Postman (tests d'API), et SQL Developer (gestion des bases de données).
  • Collaboration : Teams (communication), Klaxoon (brainstorming), Outlook (messagerie), Stream (relecture de réunions).
  • Conception UI/UX : Figma (conception UI/UX) et Crumble (respect du web design).
  • Application G2S : Cohab (gestion des accès) et Beluga (gestion de projet).
3. Architecture et modèle MVC

Le projet utilise l’architecture MVC (Modèle-Vue-Contrôleur), qui sépare la logique métier, l'affichage et les interactions utilisateur pour une gestion plus claire des responsabilités.

Le backend repose sur le framework Micronaut v4 pour la création d'applications Java, ainsi que Netty v4.1 pour la gestion des connexions réseau et Oracle 19.12 pour la base de données. Le frontend est développé avec le framework JavaScript moderne Vue.js.

Le projet utilise également une architecture microservices, aussi bien pour le backend que pour le frontend, permettant une gestion modulaire, flexible et évolutive de l’application.

Le backend inclut notamment l’utilisation de PEGA comme moteur métier pour gérer l'objet "demande".
